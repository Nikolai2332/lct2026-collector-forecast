# Модель безопасности

Кратко для жюри и заказчика: как сервис защищён в production и чем ограничен прототип. Найденные при аудите проблемы и их исправление — в [SECURITY_AUDIT.md](SECURITY_AUDIT.md), развёртывание — в [DEPLOY_VPS.md](DEPLOY_VPS.md).

## Два режима

| | demo (по умолчанию) | production (`APP_ENV=production`) |
|---|---|---|
| Запуск | `docker compose up --build` | `docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build` |
| Кто доступен снаружи | фронтенд на `:8080`; API (`:8000`) и БД (`:5432`) — только с этой машины (127.0.0.1) | только Caddy на 80/443 (TLS); API, БД и Nginx фронтенда — внутри docker-сети |
| Демо-пользователи | есть, быстрый выбор роли на экране входа | заблокированы при каждом старте; быстрого выбора нет |
| Первый администратор | `admin` / `admin123` | из `ADMIN_USERNAME` / `ADMIN_PASSWORD` или `python -m app.bootstrap user` |
| Секреты | значения по умолчанию из compose | обязательны в `.env`; со слабыми API не стартует |
| Swagger `/docs` | открыт | выключен (`DOCS_ENABLED=true` включает, но порт API всё равно закрыт) |
| Демо-данные | засеваются в пустую базу | нет (`SEED_ON_START=false`); данные — из копии БД или ETL |
| Симуляция потока (`/api/sim/*`) | включена | выключена (`SIM_ENABLED=true` включает для показа) |

При `APP_ENV=production` API отказывается стартовать (код выхода 1, до миграций), если:
- `JWT_SECRET` короче 32 символов, взят из примера или содержит `change-me` / `dev-secret`;
- пароль БД короче 12 символов или из списка слабых (`change-me`, `collector`, `postgres` …);
- `CORS_ORIGINS` пуст, содержит `*` или адреса не на `https://`;
- `JWT_EXPIRE_MINUTES` больше суток.

## Роли и области видимости

Ролевая модель заказчика (официальный ответ): «диспетчер» подразделения эксплуатации видит **дерево своего района**,
«диспетчер ОДС» (центральная диспетчерская) — **всё**, «техник» — **один комплекс**, «администратор» ИС; **роли
складываются**, **группы AD по комплексам задают область видимости**, учётные записи ведутся в AD. Из общего ТЗ
(раздел 3) сохранён руководитель подразделения — чтение и отчёты в своей области; из прототипа — инженер данных
(импорт, поток событий, симуляция). Код — `backend/app/access.py`.

- **Права** пользователя — объединение прав всех его ролей (`user_roles`).
- **Область** — объединение узлов дерева объектов (`user_scopes`: район уровня 1 или объект-комплекс уровня 2) со
  всеми поддеревьями. Если среди ролей есть «видит всё» (ОДС, инженер данных, администратор) — область не ограничена.
  Роль с областью без единого узла не видит ничего (закрыто по умолчанию).
- Роли и область читаются из БД **при каждом запросе**: изменения администратора действуют сразу.

| Право | ОДС | Диспетчер района | Техник | Руководитель | Инженер данных | Администратор |
|---|:-:|:-:|:-:|:-:|:-:|:-:|
| Область | всё | район | комплекс | район | всё | всё |
| Экраны, выгрузки XLSX/XML/CSV — в своей области (`view`, `export`) | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| Решение по прогнозу (`decide`) | ✓ | ✓ | — | — | ✓ | ✓ |
| Создать и изменить заявку, черновики из «Рекомендованных работ» (`work_orders`) | ✓ | ✓ | — | — | ✓ | ✓ |
| Сменить статус заявки (`work_order_status`) | ✓ | ✓ | ✓ только статус | — | ✓ | ✓ |
| Удалить свой черновик / любой (`delete_any_draft`) | свой | свой | — | — | свой | любой |
| Импорт CSV/XLSX/XML, поток событий, тестовая рассылка (`data_import`) | — | — | — | — | ✓ | ✓ |
| Запуск и остановка симуляции потока (`sim_control`) | ✓ | — | — | — | ✓ | ✓ |
| Настраиваемые параметры (`settings`) | — | — | — | — | — | ✓ |
| Роли и области пользователей (`users_admin`) | — | — | — | — | — | ✓ |

Как старые права легли на новые роли: прежний «диспетчер» → «диспетчер района» с областью «весь район» (в данных
заказчика район один — видит то же, что раньше); «инженер» → «инженер данных»; руководитель и администратор — без
изменений. Миграция 0007 только добавила таблицы `user_roles`, `user_scopes` и расширила список ролей: существующие
учётки получили свою роль, а роли с областью — все районы.

**Фильтрация — на сервере, везде, где есть данные датчиков и объектов:** дашборд и его кэш (ключ кэша включает
область), дерево объектов, датчики, карточка и история, прогнозы, рекомендации, журнал прогнозов и журнал событий,
выгрузки XLSX/XML/CSV, заявки, «Рекомендованные работы», «прогноз против факта», лента уведомлений и SSE, схема
коллектора (строится только из видимых объектов). Дерево загружается с областью (`ObjectIndex.load(db, access)` —
параметр обязателен, «забытая» область не превращается в «видно всё»), фильтр по датчикам добавляется в общем
`apply_channel_filters`. Чужой объект, датчик, прогноз или заявка по прямому id — **404, как несуществующие**
(существование не раскрывается); запрет по праву — 403 раньше проверки области. **SSE:** у подписчика — область на
момент подключения; уведомления (и отдельные, и сводки «ещё N») собираются для каждой области среди подписчиков
отдельно, чужие счётчики не утекают; одиночная тестовая рассылка доходит только до подписчиков, в чьей области датчик.
Метрики модели на тесте (общие Precision/Recall, по типам, PR-кривая) — свойства модели, а не данные объектов, и
показываются всем.

Администратор меняет роли и области **локальных** учёток: меню пользователя → «Пользователи и роли»
(`PUT /api/users/{id}/access`, запись `user_access_update` в журнале действий со старыми и новыми ролями и областью);
учётки из AD — только через группы каталога (409); снять с себя право управления пользователями нельзя (409).

Тесты — `tests/test_scope_matrix.py` (матрица «роль × эндпоинт × чужой объект» по всей схеме OpenAPI: 46 операций, новый эндпоинт без классификации роняет тест) и `tests/test_access.py`: матрица «роль × право» (6 ролей × 6 действий), фильтрация списков, 404 на прямые id
(10 эндпоинтов), техник меняет только статус, выгрузки XLSX/XML только своей области, кэш дашборда по областям,
SSE (свои уведомления и сводки, чужое одиночное не доходит, первый пакет потока по области), роль с областью без
узлов не видит ничего, сложение ролей и объединение областей, проверки формы администратора.

Доступ по эндпоинтам:

## Аутентификация

- Вход по логину и паролю → JWT (HS256, алгоритм зафиксирован, `exp` обязателен) на `JWT_EXPIRE_MINUTES` (720 минут — смена 12 ч). Токен передаётся только в заголовке `Authorization: Bearer`; в адресе JWT не принимается.
- Пароли — PBKDF2-HMAC-SHA256, 600 000 итераций, соль на пользователя, сравнение за постоянное время. Для несуществующего логина выполняется та же работа — по времени ответа нельзя узнать, есть ли пользователь. Ответ в обоих случаях одинаковый: «Неверный логин или пароль».
- Защита от перебора: после 5 неудачных входов за 5 минут для пары «IP + логин», 30 для IP или 20 для логина со всех адресов вместе (перебор одного пароля с многих адресов) — ответ 429 до конца окна. В Nginx дополнительно не больше 60 запросов входа в минуту с IP (+20 всплеском) и 50 запросов к API в секунду (+200): вся смена может выходить через один корпоративный NAT, при прежних 10 входах в минуту нагрузочный тест с 30 пользователями за одним адресом получал 429 ([LOADTEST.md](LOADTEST.md)). Перебор по-прежнему останавливает счётчик неудачных входов в API.
- Уведомления (SSE): `EventSource` не умеет заголовки, поэтому браузер сначала берёт по JWT одноразовый тикет (`POST /api/notifications/ticket`, 60 секунд) и подключается с `?ticket=`. Тикет сгорает при подключении; при обрыве берётся новый.
- Пароли пользователей задаёт администратор сервера: `docker compose … exec api python -m app.bootstrap user <логин> --role <роль> [--role …] [--scope <id объекта> …]` (не короче 12 символов, не из демо-набора).

## Транспорт и прокси

- TLS — Caddy (`deploy/Caddyfile`): сертификат Let's Encrypt получается и продлевается автоматически, HTTP → HTTPS, HSTS на год.
- Nginx фронтенда: `Content-Security-Policy` (скрипты только с того же адреса, `frame-ancestors 'none'`), `X-Content-Type-Options`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `Permissions-Policy`; версия сервера скрыта; тело запроса до 1 МБ (импорт — 50 МБ, поток событий — 10 МБ); таймауты чтения запроса.
- Журнал запросов Nginx пишется без query-строк; журнал доступа uvicorn выключен; Caddy журнал запросов не ведёт.
- Реальный IP клиента: Caddy ставит `X-Forwarded-For` сам, Nginx берёт его из частной сети docker и передаёт в API только его.
- CORS: явный список источников, без cookie и credentials; в production — только `https://<домен>`.

## Ввод данных

- Все фильтры и поиск — через ORM с параметрами, сортировки — из белого списка.
- XML (поток событий, импорт): разбор только через `defusedxml` с `forbid_dtd`, `forbid_entities`, `forbid_external` — XXE (чтение локальных файлов и SSRF через внешние сущности), «миллиард смешков» и внешние DTD отклоняются с 422 до разбора содержимого (тесты `tests/test_xml.py`); тело потока — до 10 МБ (413 раньше разбора), те же схемы проверки, что у JSON. Выгрузка XML строится стандартным `ElementTree` (экранирование — его).
- Импорт CSV/XLSX/XML: тип проверяется и по расширению, и по содержимому; для XLSX до разбора считается размер после распаковки (защита от zip-бомб); до 50 МБ и 300 000 строк (больше — через ETL); имя файла очищается; не больше 20 загрузок за 10 минут на пользователя.
- Выгрузка журнала в XLSX: значения, которые Excel принял бы за формулу (`= + - @` …), пишутся как текст.
- «Машина времени» `at` — от 2000 до 2200 года; даты у края календаря в любых параметрах — 422, а не 500.
- Загрузчик среза для экспертов (`scripts/load_expert_slice.py`) берёт из `manifest.json` архива только то, что совпадает с белым списком таблиц и колонок в коде; рабочие (не демо) решения, заявки и области видимости заменяет только с `--force` и пишет загрузку в `audit_log`.
- Длины полей ограничены схемами (логин 64, пароль 256, комментарий 2000, описание заявки 4000 символов, пачка событий до 10 000).
- Фронтенд не вставляет HTML из API: всё выводится текстом React.

## Журнал действий (`audit_log`)

Каждая запись: время, пользователь, действие, объект, подробности, IP клиента. Пишутся: вход (`login`), неудачный вход (`login_failed`, с логином, без пароля), решение по прогнозу, создание, изменение и удаление заявки, импорт файла и приём событий, выгрузка журнала, тестовая рассылка, запуск и остановка симуляции (`sim_start` с сутками и скоростью, `sim_stop` с модельным временем), изменение настроек (`settings_update` со старыми и новыми значениями), создание заявки с правилом рекомендации и источником (`work_order_create`: `rule_id`, `source` — `manual` или `maintenance_plan`), неудачный вход через LDAP (`login_failed`, причина `ldap` или `ldap_unavailable`), блокировка демо-учёток, создание администратора и пользователей через `bootstrap` (`user_set` с ролями и областью), изменение ролей и области администратором (`user_access_update`: было/стало), выгрузки журнала событий и решений (`export_events`, `export_decisions`), загрузка среза для экспертов (`expert_slice_load`). Пароли и токены в журнал и в логи не попадают.

## Резервные копии

Контейнер `backup` (production) делает `pg_dump -Fc` раз в `BACKUP_INTERVAL_HOURS` (24 ч) в `./backups` и хранит `BACKUP_KEEP` (14) последних копий. Разовая копия: `… exec backup sh /backup.sh once`. Восстановление: `./deploy/restore.sh backups/<файл>.dump` (API на это время останавливается). Копии нужно регулярно увозить с сервера — порядок в [DEPLOY_VPS.md](DEPLOY_VPS.md). Восстановление проверено: копия рабочей базы (7,4 ГБ) восстановлена в чистый production-стек, после чего сервис отвечает на реальных данных.

## LDAP / Active Directory

При `LDAP_ENABLED=true` вход — только через корпоративный каталог (`app/ldap_auth.py`, библиотека `ldap3`); локальные
пароли не проверяются, обходного пути нет. Порядок:

1. Bind сервисной учёткой `LDAP_BIND_DN` / `LDAP_BIND_PASSWORD` (права — только чтение). Соединение — `ldaps://` или
   StartTLS (`LDAP_START_TLS=true`) с обязательной проверкой сертификата (`ssl.CERT_REQUIRED`; свой корневой
   сертификат — `LDAP_CA_FILE`). **В production открытый `ldap://` без StartTLS не стартует** (`app.config.production_problems`).
2. Поиск пользователя по `LDAP_USER_FILTER` (AD: `(sAMAccountName={username})`, OpenLDAP: `(uid={username})`).
   Логин проверяется по шаблону (буквы, цифры, `. _ @ -`, до 64 символов) и экранируется `escape_filter_chars` —
   LDAP-инъекция `*)(uid=*` не проходит (тест). Найдено не ровно одна запись — отказ.
3. Пароль проверяется bind-ом найденного DN отдельным соединением. Пустой пароль отвергается заранее (bind с пустым
   паролем в LDAP — «анонимный» и считается успешным).
4. Группы пользователя — атрибут `memberOf` и поиск групп `LDAP_GROUP_FILTER` (по умолчанию
   `(|(member={user_dn})(uniqueMember={user_dn}))`) в `LDAP_GROUP_BASE_DN` или `LDAP_BASE_DN`. Роль — по
   `LDAP_ROLE_GROUPS`: `роль:группа` через запятую (группа — первая часть DN, `cn=dispatchers`) или через `;` с полными
   DN. **Роли складываются**: пользователь получает все роли, чьи группы у него есть. Нет ни одной — отказ.
   **Область видимости** — по `LDAP_SCOPE_GROUPS`: `id объекта:группа` (район или объект-комплекс), объединение узлов
   всех групп пользователя. Если все роли пользователя — с областью (диспетчер района, техник, руководитель), а группы
   области нет или она указывает на несуществующий объект — **отказ** (закрыто по умолчанию). Ошибка разбора
   `LDAP_SCOPE_GROUPS` — 503, как у `LDAP_ROLE_GROUPS`.
5. Локальный профиль в `users` (`auth_source=ldap`, без пароля) создаётся при первом входе; ФИО, роли и область обновляются
   при каждом входе из каталога. Заблокированный локально профиль (`is_active=false`) не входит. Если логин совпадает
   с **локальной** учётной записью (без учёта регистра: `ADMIN` = `admin`, как в AD), вход через LDAP отклоняется —
   чужой каталог не может «перехватить» локального администратора. В production группы задавайте полными DN через
   `;`: короткая форма `cn=…` совпадает с группой с таким именем в любой ветке каталога.

Ответы: неверный логин или пароль, нет группы, конфликт — 401 «Неверный логин или пароль» (одинаково для всех
случаев), в `audit_log` — `login_failed` с причиной `ldap`; каталог недоступен, сервисная учётка не прошла bind,
TLS не сходится (например, просроченный сертификат) — **503**, вход закрыт, причина `ldap_unavailable`. Счётчик
неудачных входов и лимиты работают так же, как для локальных паролей.

Проверено: автотесты на mock-сервере ldap3 (`tests/test_ldap.py`: роли по `memberOf` и по группам, неверный и пустой
пароль, нет в каталоге, нет группы, неоднозначный логин, конфликт с локальной учёткой, инъекция, недоступный сервер,
заблокированный профиль, production без TLS, сложение ролей, техник с группой комплекса видит один комплекс, техник
без группы комплекса и с группой на несуществующий объект — отказ, разбор `LDAP_SCOPE_GROUPS`) и **вживую против
OpenLDAP** по `ldaps://` с проверкой сертификата — `deploy/ldap-test/` (26.09, 11 из 11: диспетчер района через группу
района видит все 16 комплексов, **техник через группу комплекса — только «объект Альфа»**, ОДС и администратор — всё,
техник без группы комплекса — 401, неверный пароль, нет группы, нет в каталоге, инъекция, локальный пароль при
включённом LDAP; раньше — остановка OpenLDAP — 503). Встроенный в образ OpenLDAP УЦ 2021 года оказался

## Симуляция потока

- Только читает прогнозы и исходы и двигает «модельные часы» (`sim_state`); данные не меняет. Скрипт шлёт события в обычный `POST /api/ingest/events` с теми же правилами и ролями; уже загруженные события пропускаются как дубли.
- Параметры ограничены: скорость 1–600, сутки — только с прогнозами (422), одна симуляция за раз (условный `UPDATE … WHERE active = false` в БД → 409). После перезапуска API симуляция всегда сброшена.
- Пока она идёт, «Сейчас» у **всех** пользователей — модельное время (метка в шапке и подсказка это объясняют). Поэтому в production она по умолчанию выключена: на рабочем сервере диспетчеры не должны внезапно оказаться в модельном времени. Включать `SIM_ENABLED=true` — только на стенде для показа.
- Скрипт по умолчанию входит демо-инженером; в production логин и пароль — только через `SIM_USERNAME`/`SIM_PASSWORD`, пароль в командную строку не передавайте (он попадёт в историю оболочки).

## Ограничения прототипа

- Лимиты входа, тикеты SSE, копия состояния симуляции и планировщик (APScheduler) живут в одном процессе API. При нескольких воркерах или репликах их нужно перенести в PostgreSQL или Redis и вынести планировщик в отдельный процесс.
- JWT нельзя отозвать до истечения срока (выход — удаление токена в браузере); заблокированный пользователь теряет доступ сразу.
- Токен хранится в `localStorage`: от кражи через XSS защищают строгий CSP и отсутствие вставки HTML.
- Нет двухфакторной аутентификации и смены пароля из интерфейса (пароли задаёт администратор сервера).
- В demo-режиме клиент с этой же машины может подставить `X-Forwarded-For` и исказить IP в журнале; в production единственный вход — Caddy.
- `react-router-dom` 6 с двумя уязвимостями средней серьёзности (переход на v7 — после хакатона, [SECURITY_AUDIT.md](SECURITY_AUDIT.md), S-20).
