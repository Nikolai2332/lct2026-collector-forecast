# Смоделированный журнал решений диспетчера

Журнала ОДС и решений диспетчеров у заказчика нет (ответ организаторов 23.09: «делаем без них»); решения
предлагается **моделировать правдоподобно, «а не просто случайными числами»**. В сервисе это делает скрипт
`backend/scripts/simulate_decisions.py`. Каждое такое решение помечено `source = simulation` в базе
(`decisions.source`, миграция 0008), в API (`DecisionOut.source`) и в выгрузке; в интерфейсе рядом с ним —
серый бейдж **«смоделировано»** (журнал, карточка датчика, история решений). Решения людей — `source = user`.

## Модель поведения диспетчера

Параметры — в начале скрипта; всё детерминировано (фиксированное зерно), повторный запуск даёт тот же журнал.

| Что | Правило |
|---|---|
| Что разбирает | уведомления, которые диспетчер реально видит: новые переходы в «Критично» (как колокольчик и SSE) и 15 % прогнозов «Риск» тех же суток |
| Сколько успевает | днём 92 %, ночью (0–7 ч) 80 %; остальное остаётся «Нет решения» |
| Задержка реакции | логнормальная: медиана 12 мин днём, 25 мин ночью, не больше 3 ч |
| Сбывшийся прогноз | «Выезд бригады» 65–85 % (чем выше вероятность, тем чаще), иначе «Наблюдение», изредка (5 %) «Ложное срабатывание» |
| Несбывшийся | «Ложное срабатывание» 50 %, «Наблюдение» 38 %, «Выезд» 12 % — диспетчер не знает будущего |
| Причина из справочника | по виду события: газ в будни 9–14 → «Проводятся плановые работы»; потеря связи → «Пропадание связи» / «Сбой канала связи»; фазы и ИБП → «Обесточивание»; датчики затопления → «Риск затопления»; двери и движение → «Проход персонала»; иначе — по весам |
| Кто решил | активные пользователи с ролями «Диспетчер ОДС» и «Диспетчер района» |
| Комментарий | «Смоделировано: журнала ОДС нет (source=simulation)» |

Модель «знает» исход прогноза — это и делает историю правдоподобной (сбывшиеся чаще закрывались выездом), но
шум не даёт ей стать идеальной. Тест `tests/test_simulated_decisions.py` проверяет на 10 000 розыгрышах, что
распределение не равномерное и зависит от исхода и вероятности, что всё помечено и что запуск повторяем.

## Запуск — только явно

Не при старте, не в сиде и не в production (без `--force`):

```bash
docker compose exec api python -m scripts.simulate_decisions --from 2026-06-01 --to 2026-06-30
```

Повторный запуск за тот же период сначала удаляет прежние смоделированные решения этого периода; решения людей
не трогает. Для среза экспертов ([EXPERT_SLICE.md](EXPERT_SLICE.md)) — после загрузки среза.

## Как решения замыкают цикл «дообучения» (общий ТЗ, сценарии п. 12)

1. Диспетчер принимает решение по прогнозу с причиной из справочника (`POST /api/predictions/{id}/decision`) —
   или решения моделируются, пока настоящих нет.
2. Разметка исходов (`app/scheduler/outcomes.py`) через 24 ч отмечает, сбылся ли отказ.
3. `GET /api/export/decisions?date_from=…&date_to=…&source=all|user|simulation` — CSV «решение + прогноз + исход»:
   вероятность, уровень риска, версия модели, тип решения, код причины, реакция в минутах, сбылся ли отказ, вид
   отказа. Только датчики области пользователя, выгрузка — в журнале действий.
4. Этот набор — обратная связь для конвейера `ml/`: какие тревоги диспетчеры систематически закрывают как ложные
   и по какой причине (например, «плановые работы» по газу в будни — кандидат в признак или в правило-фильтр),
   где модель пропускает отказы. При переобучении (`ml/README.md`) решения с `source = user` можно использовать
   как дополнительную разметку и для выбора порога по «комфортной» для смены частоте тревог.

**Автоматического переобучения нет** (осознанно): решений людей пока нет, а смоделированные нельзя подмешивать
в обучение — модель выучила бы правила генератора. Переобучение — ручной запуск конвейера `ml/` с проверкой на
тесте, как для v3.
