# Сверка с общим ТЗ хакатона

Общий ТЗ — документ организаторов хакатона (PDF, в репозиторий не входит). Здесь — требования разделов 4–13: статус и где это в
проекте. Команда выбрала направление **«Отказ датчика»**; требования про прогноз инцидентов (пожар, подтопление,
проникновение) относятся к другим направлениям — где это так, сказано прямо.

Статусы: **выполнено**, **частично** (что именно нет и почему), **нет** (почему).

## 4. Постановка задачи

| Требование | Статус | Где |
|---|---|---|
| Автоматизированное выявление потенциальных рисков | выполнено | прогноз отказа на 24 ч по каждому датчику, уровни риска, топ-20 и схема объектов на дашборде |
| Оптимизация работы диспетчерской службы за счёт аналитических данных | выполнено | причины прогноза языком диспетчера, решение с причиной из справочника, заявка в один клик, уведомления только о новых переходах в «Критично» ([API.md](API.md)) |
| Повышение эффективности технического обслуживания | выполнено | рекомендации по ТО по состоянию, «Рекомендованные работы» ([RECOMMENDATIONS.md](RECOMMENDATIONS.md)) |
| Прогнозирование отказов датчиков и инженерных систем до их возникновения | выполнено для датчиков | LightGBM, горизонт 24 ч, модель `lgbm-2026.09-v3`, тест 2026: Precision 0,696, Recall 0,571, PR-AUC 0,618 ([ML_REPORT.md](ML_REPORT.md), раздел «Версия 3»); агрегаты (насосы, вентиляторы, фазы, ИБП) — через их датчики состояния |
| Раннее выявление рисков пожаров и подтоплений | нет — другое направление | направление «Отказ датчика»; отказ пожарных датчиков и датчиков затопления прогнозируется, сами пожары и подтопления — нет |
| Аналитическая поддержка при верификации фактов несанкционированного доступа | частично | прогноз отказа охранных датчиков (двери, люки, движение, стекло — Precision 0,69–0,92 на тесте) и рекомендация «Сначала удалённая проверка» для типов с низкой точностью; верификация самих проникновений — другое направление |
| Рекомендации по ТО на основе данных о состоянии оборудования | выполнено | движок правил: вид отказа, история, соседи, питание, заявки → действие, обоснование, приоритет, срок, исполнитель ([RECOMMENDATIONS.md](RECOMMENDATIONS.md)); проект правил, требует согласования |

## 5. Границы решения

| Требование | Статус | Где |
|---|---|---|
| Анализ исторических и текущих данных мониторинга | выполнено | 313 млн событий 2019–2026 (ETL → Parquet), оперативный контур — `events_recent`, поток — `POST /api/ingest/events` |
| Обработка журналов диспетчерской службы | частично | журналов ОДС заказчик не предоставит (ответ организаторов 23.09); решения диспетчеров ведутся в сервисе (`decisions`) и попадают в журнал прогнозов; по совету организаторов решения можно **смоделировать правдоподобно** (`scripts/simulate_decisions`, пометка «смоделировано», [SIMULATED_DECISIONS.md](SIMULATED_DECISIONS.md)); журнал тревожных событий СМВУ с контекстом — вкладка «События» |
| Работа с реестрами оборудования | выполнено | справочники объектов и каналов (импорт CSV/XLSX/XML); реестра ремонтов нет у заказчика |
| Прогнозы с вероятностью и временным горизонтом | выполнено | `prob`, `horizon_h = 24`, индекс здоровья, уровень риска |
| Предиктивное моделирование на исторических данных | выполнено | `ml/`, валидация по времени, тест открыт один раз |
| Интеграция с системами мониторинга для получения данных | выполнено (API) | `POST /api/ingest/events` (JSON/XML), импорт; только чтение из внешних систем — сервис ничего в них не пишет |
| Не замещать диспетчера, не принимать окончательных решений, не управлять оборудованием | выполнено | решение всегда за диспетчером (причина обязательна), рекомендации — «проект правил», управления оборудованием нет |
| Точность прогнозов не ниже установленных показателей | частично | цель Precision > 0,7 / Recall > 0,5: v3 — Recall 0,571 (выполнен), Precision 0,696 (на 0,004 ниже плана) на тесте 2026; обоснование — [ML_REPORT.md](ML_REPORT.md), «Обоснование целевых метрик»; организаторы: плановые значения можно снижать с обоснованием |
| Своевременное информирование | выполнено | SSE, всплывающие уведомления со звуком, колокольчик; задержка ≈ 1 с в симуляции ([ARCHITECTURE.md](ARCHITECTURE.md#задержка-потоковых-данных)) |
| Удобный интерфейс, надёжная интеграция, защита от НСД | выполнено | [FRONTEND_DECISIONS.md](FRONTEND_DECISIONS.md), REST + OpenAPI, [SECURITY.md](SECURITY.md) |

| Потоковые данные СМВУ — API/очередь сообщений | выполнено (API) | `POST /api/ingest/events`, до 10 000 событий за раз; очереди сообщений нет |
| Журналы ОДС — загрузка через API | частично | формата журнала ОДС нет (данных не будет); решения диспетчеров — `POST /api/predictions/{id}/decision` |

| Программный обмен (API) JSON, XML | выполнено | JSON — все эндпоинты; XML — приём потока, импорт, выгрузка журнала (`format=xml`), безопасный разбор `defusedxml` ([API.md](API.md#обмен-xml)) |

| Обфускация на стороне источника | не требуется от сервиса | данные заказчика уже обезличены; в репозитории их нет |
