# Нагрузочная проверка

ТЗ (раздел 11): «одновременная работа не менее 20 пользователей без деградации производительности». Проверено на
20 и 40 виртуальных пользователях (в два раза больше требования) — на изолированном стеке с демо-данными (с записью)
и на основном стеке с реальными данными (только чтение). **Итог: 20 пользователей — без деградации (p95 180–350 мс,
0 ошибок); 40 — без ошибок, медленнее (p95 0,7–1,2 с).** По ходу найдены и исправлены четыре узких места.

## Как проверяли

- **Инструмент:** [locust](https://locust.io) 2.43.1 в контейнере `locustio/locust`, сценарий —
  [`loadtest/locustfile.py`](../loadtest/locustfile.py). Запросы идут **через Nginx фронтенда** (как у браузера),
  все пользователи — с одного адреса (самый тяжёлый случай: вся смена за одним корпоративным NAT).
- **Пользователи и роли:** по кругу диспетчер ×4, инженер ×2, руководитель, администратор; пауза между действиями
  1–3 с («человек думает»). Каждый входит и дальше ходит по сценарию диспетчера: дашборд (плашки, топ-20, лента
  уведомлений), схема объектов, журнал с фильтрами (уровень риска; «без решения + сбылся»), карточка датчика
  (карточка, график за 30 дней, рекомендация по ТО), заявки и «Рекомендованные работы», поток SSE до первого
  события `snapshot`. С `WRITE=1` диспетчеры и инженеры ещё отмечают решения («Наблюдение») и создают черновик
  заявки, который тут же удаляют.
- **Стенды** (одна машина: Windows 11, Docker Desktop; API — один процесс uvicorn, PostgreSQL 16):
  - изолированный `docker compose -p recs` с демо-данными (400 датчиков), момент 01.08.2026 12:00, **с записью**;
  - основной стек с реальными данными (11,0 млн прогнозов, 7 654 датчика в срезе), момент 29.06.2026 23:00,
    **только чтение** (решений и заявок тест не создаёт — база не засоряется).
- Прогон — 4 минуты после разгона (4 пользователя в секунду). CPU контейнеров — `docker stats` каждые 8 с.

```bash
# изолированный стек, с записью
docker run --rm -v "$PWD/loadtest:/mnt/locust" -e LOAD_AT=2026-08-01T12:00:00 -e WRITE=1 locustio/locust:2.43.1 \
  -f /mnt/locust/locustfile.py --headless -u 40 -r 4 -t 4m --host http://host.docker.internal:19180 \
  --csv /mnt/locust/results/recs_40u --only-summary
# основной стек с реальными данными, только чтение
docker run --rm -v "$PWD/loadtest:/mnt/locust" -e LOAD_AT=2026-06-29T23:00:00 -e WRITE=0 locustio/locust:2.43.1 \
  -f /mnt/locust/locustfile.py --headless -u 40 -r 4 -t 4m --host http://host.docker.internal:8080 \
  --csv /mnt/locust/results/real_40u --only-summary
```

Пароли пользователей — переменные `PASS_DISPATCHER`, `PASS_ENGINEER`, `PASS_MANAGER`, `PASS_ADMIN` (по умолчанию —
демо). Сводки прогонов — `loadtest/results/*_summary.txt`.

отдельный процесс ([ARCHITECTURE.md](ARCHITECTURE.md), [SECURITY.md](SECURITY.md)).

## Что нашли и исправили

| Узкое место | Как проявилось | Исправление | Стало |
|---|---|---|---|
| Лимиты Nginx «10 входов в минуту» и «20 запросов/с» с адреса | 30 пользователей за одним адресом: 70 из 76 входов — 429, в работе оставалось 6 пользователей | Лимиты рассчитаны на 40 пользователей за одним NAT: вход 60/мин (+20 всплеском), API 50/с (+200). Перебор паролей по-прежнему останавливает API: 5 неудачных входов на логин и 30 на адрес за 5 минут | 40 пользователей входят без 429 |
| Пул соединений с БД кончался | Реальные данные, 40 пользователей: 52 ответа 500 через 30 с (`QueuePool limit of size 5 overflow 10 reached`), p95 30 с | Настраиваемые параметры перечитывает из БД один поток, а не каждый запрос вторым соединением (`app/runtime_settings.py`); пул PostgreSQL 10 + 30 (`DB_POOL_SIZE`, `DB_MAX_OVERFLOW`) под 40 потоков обработчиков | 0 ошибок, p95 1,2 с |
| Подсчёт строк журнала читал все прогнозы | Реальные данные, 20 пользователей: журнал p50 0,97 с, p95 1,8 с; в плане запроса — Parallel Seq Scan по 11 млн строк | Условие «тревожные или с решением» — через список id прогнозов с решением, а не OR с подзапросом (индекс `ix_predictions_at_risk` снова работает); соединения с исходами и решениями — только когда по ним фильтруют. Рекомендации в журнале дешевле: группы типов датчиков считаются один раз, датчики объектов считаются в SQL | Подсчёт 0,6 → 0,07 с; журнал p50 0,34 с, p95 0,74 с |
| «Рекомендованные работы» считались при каждом запросе | 1,4 с на реальных данных, под нагрузкой p50 2,6 с, p95 5 с | Результат кэшируется (срез, объект, версия заявок и файла правил; прогнозы, исходы и настройки сбрасывают кэш) и прогревается при старте API | p50 0,05 с, p95 0,1 с |
| Гонка в списке заявок | Демо с записью, 40 пользователей: 1 ответ 500 (`KeyError`) — черновик удалили между двумя запросами списка | Удалённые между запросами заявки пропускаются (`load_work_orders`), тест | 0 ошибок |

Для сравнения — до исправлений: реальные данные, 20 пользователей — p50 140 мс, p95 1,2 с, журнал p95 1,8 с,
«Рекомендованные работы» p95 5 с; 40 пользователей — 52 ошибки 500, p95 30 с.
