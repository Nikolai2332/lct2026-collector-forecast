# API — краткий обзор

Полный контракт — Swagger на `/docs` и файл [`backend/openapi.json`](../backend/openapi.json). Здесь — что есть и как этим пользоваться.

## Общие правила

- **Авторизация:** `Authorization: Bearer <JWT>`. Токен выдаёт `POST /api/auth/login`. Без токена — 401, без прав — 403. Открыт только `/api/health`.
- **Область видимости:** все ответы с данными датчиков и объектов (дашборд, объекты, датчики, прогнозы, журналы, заявки, рекомендованные работы, уведомления и SSE, схема, выгрузки, «прогноз против факта») — только по датчикам области пользователя. Чужой объект, датчик, прогноз или заявка по прямому id — **404**, как несуществующие; `object_id` вне области в фильтре — тоже 404. Метрики модели на тесте (`/api/model/metrics`: overall, по типам, PR-кривая) — общие для модели, не данные объектов.
- **Машина времени:** все GET принимают `at` (ISO 8601). Без пояса — московское время, с поясом — переводится в МСК. Не задан — сейчас, а во время симуляции потока — модельное время (см. «Симуляция потока»). Прогнозы берутся из последнего среза не позже `at`.
- **Время** во всех ответах — московское, без пояса: `2026-08-01T18:42:10`.
- **Списки:** `limit` (1–500, по умолчанию 50) и `offset`; в ответе `total`. Фильтры применяются на сервере.
- **Ошибки:** `{"detail": "текст"}` на русском. У 422 от валидации — список `{"loc", "msg", "type"}` в формате FastAPI с русским `msg`.
- **Уровни риска:** по умолчанию — как у ML: `normal` (≥80 здоровья), `attention` (50–79), `risk` (20–49), `critical` (<20), то есть вероятность 0,2 / 0,5 / 0,8. Администратор может изменить границы («Настройки», `PUT /api/settings`) — тогда `risk_level` во всех ответах, фильтрах и счётчиках пересчитывается от `prob` сразу, без перезапуска; прогнозы в БД не меняются.

## Роли

Роли заказчика складываются; права — объединение прав ролей, область — объединение узлов (подробно —
[SECURITY.md](SECURITY.md#роли-и-области-видимости)). `GET /api/auth/me` и вход возвращают `roles`, `scope`,
`scope_label`, `unrestricted`, `permissions` — фронтенд прячет кнопки по `permissions`, проверка — на сервере.

| Действие (право) | ОДС `dispatcher_ods` | район `dispatcher` | `technician` | `manager` | `engineer` | `admin` |
|---|:-:|:-:|:-:|:-:|:-:|:-:|
| Область | всё | район | комплекс | район | всё | всё |
| Чтение экранов, выгрузки XLSX/XML/CSV (`view`, `export`) | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| Решение по прогнозу (`decide`), создание и правка заявок (`work_orders`) | ✓ | ✓ | — | — | ✓ | ✓ |
| Смена статуса заявки (`work_order_status`) | ✓ | ✓ | ✓ (только статус) | — | ✓ | ✓ |
| Импорт, поток событий, тестовая рассылка (`data_import`) | — | — | — | — | ✓ | ✓ |
| Симуляция потока (`sim_control`) | ✓ | — | — | — | ✓ | ✓ |
| Настройки (`settings`), роли и области (`users_admin`) | — | — | — | — | — | ✓ |

## Эндпоинты

### Сервис и вход

| Метод и путь | Назначение |
|---|---|
| `GET /api/health` | статус, версия сервиса и модели, доступность БД |
| `POST /api/auth/login` | вход (JSON `{username, password}`) → `{access_token, expires_in, user}`. При `LDAP_ENABLED=true` — только через каталог LDAP/AD; каталог недоступен — 503 ([SECURITY.md](SECURITY.md)) |
| `POST /api/auth/token` | то же через форму OAuth2 — для кнопки Authorize в Swagger |
| `GET /api/auth/me` | текущий пользователь: роли, область (`scope`, `scope_label`), права (`permissions`) |
| `GET /api/users` | администратор: пользователи с ролями и областями |
| `PUT /api/users/{id}/access` | администратор: `{roles: [...], scope_object_ids: [...]}` локальному пользователю. Область — район или объект-комплекс (уровень 1–2), обязательна для ролей с областью (422); учётка из LDAP — 409 (роли из групп AD); снять с себя `users_admin` — 409. Пишется в `audit_log` (`user_access_update`, было/стало) |

### Дашборд и схема объектов

| Метод и путь | Назначение |
|---|---|
| `GET /api/dashboard/summary` | 4 плашки: датчики в зоне риска, прогнозы отказов на 24 ч, открытые заявки, точность за 30 дней; распределение по уровням риска |
| `GET /api/objects` | дерево «район → объект → подобъект»; у узла `max_risk_level`, `risk_counts`, `channels_count`. Фильтры `system_type`, `sensor_type` |
| `GET /api/objects/{id}` | объект, путь, дочерние объекты и страница его датчиков (включая вложенные) по убыванию риска |

### Схема коллекторов (GeoJSON, WKT)

Геометрия **синтетическая** (координат у заказчика нет): условные метры, 1 ПК = 10 м; в ответе `synthetic: true` и
`crs_note`. Правила и покрытие — [GEO_SCHEME.md](GEO_SCHEME.md).

| Метод и путь | Назначение |
|---|---|
| `GET /api/geo/collectors` | `object_id`, `at`, `format=geojson|wkt`. Объекты `kind`: `collector` (MultiLineString — основное тело и галереи, счётчики риска), `section` (участок подобъекта), `node` (узел подобъекта без пикетов), `problem_zone` (скопление тревожных датчиков на оси); `stats` — покрытие разбора пикетов |
| `GET /api/geo/channels` | точки датчиков: `object_id`, `system_type`, `sensor_type`, `risk_level` (несколько), `at`, `format`; свойства — риск и вероятность на срез, подпись пикета, `placed_by` (picket / gallery / node), сторона |

`format=wkt` — `items` со свойствами и строкой `wkt` (`MULTILINESTRING (…)`, `LINESTRING (…)`, `POINT (…)`).

### Датчики

| Метод и путь | Назначение |
|---|---|
| `GET /api/channels` | датчики с прогнозом на `at`. Фильтры: `object_id` (с вложенными), `system_type`, `sensor_type`, `risk_level` (несколько), `q` (название/тег/id); `sort=risk|name` |
| `GET /api/channels/{id}` | карточка: тег и его уровни, актуальный прогноз с факторами и историей решений, последнее событие, «на контроле», открытые заявки |
| `GET /api/channels/{id}/history` | график: `granularity=day` (из `channel_daily`, до 90 дней) или `hour` (из событий, до 30 дней = 720 точек); отметки отказов `faults[{ts, kind}]` трёх видов разметки ML — «Неисправен», «Отключено устройство», «Пропадание связи» (из `channel_faults` и статусов в событиях, без дублей); история прогнозов |

### Прогнозы и решения

| Метод и путь | Назначение |
|---|---|
| `GET /api/predictions` | прогнозы на `at` по убыванию вероятности — **формат из ТЗ фронтенда**. Фильтры: `risk_level`, `min_prob`, `object_id`, `system_type`, `sensor_type`, `q` |
| `GET /api/predictions/{id}` | то же + `at`, `horizon_h`, `model_version`, `factors_detail` (признак, значение, норма, фраза), история решений |
| `GET /api/predictions/{id}/recommendation` | рекомендация по ТО для прогноза — см. «Рекомендации по ТО» |
| `POST /api/predictions/{id}/decision` | решение: `{decision_type: dispatch|false_alarm|monitor, reason_id, comment?}`. **Без `reason_id` — 422.** Причина должна подходить к решению |

Пример `GET /api/predictions?at=2026-08-01T12:00:00&limit=1`:

```json
{
  "at": "2026-08-01T12:00:00",
  "total": 400,
  "items": [{
    "prediction_id": 50401,
    "channel": {"id": 334609, "name": "Дым ПК 1101+2", "sensor_type": "Датчик дыма", "system_type": "Пожарная охрана"},
    "object": {"id": 20, "name": "объект Фита", "path": ["Район по эксплуатации", "объект Бета", "объект Фита"]},
    "prob": 0.87,
    "health": 13,
    "risk_level": "critical",
    "factors": [
      "Сообщений о неисправности за сутки: 6 (обычно 0)",
      "Смен статуса за сутки: 40",
      "Отказов в этом объекте за 7 дней: 3"
    ],
    "factors_human": [
      {"text": "6 сообщений «Неисправен» за сутки (обычно 0)", "short": "6 сообщений «Неисправен» за сутки (обычно 0)",
       "features": ["fault_msgs_24h"], "tech": ["Сообщений о неисправности за сутки: 6 (обычно 0)"]},
      {"text": "Статус менялся 40 раз за сутки (обычно 2) — дребезг", "...": "..."},
      {"text": "3 отказа у других датчиков этого объекта за 7 дней", "...": "..."}
    ],
    "outcome": {"happened": true, "fault_at": "2026-08-01T18:42:10"},
    "decision": null,
    "work_order_id": null
  }]
}
```

**Причины прогноза.** `factors` — технические формулировки ML, как в ТЗ (не менялись). `factors_human` — те же причины
языком диспетчера, строятся при выдаче (`backend/app/factors_human.py`, таблицы не меняются): по коду признака
и значению — фраза («Датчик молчит 5 сут 10 ч — обычно выходит на связь хотя бы раз в 5 сут 16 ч. Через ~6 ч связь
будет считаться потерянной»), признаки об одном и том же (пять признаков текущей паузы связи, окна одного счётчика)
склеены в один довод, поэтому доводов может быть меньше трёх. `short` — до 60 символов для таблиц, `tech` — исходные
фразы ML для подсказки «Подробнее для аналитика». «обычно N» — типичное значение у датчиков того же типа. Те же
формулировки — в журнале, XLSX (колонки «Причины» и «Причины (формулировки модели)»), уведомлениях и описании заявки.

**Вид отказа (v3).** `kind_probs` — вероятности видов отказа от модели `lgbm-2026.09-v3`: `{"link": …, "fault": …,
"disconnected": …, "value": …}` (потеря связи, «Неисправен» — потеря связи с устройством, «Отключено устройство», сбой
значения), в сумме — `prob`. Заполнены у прогнозов с `prob ≥ 0,2` (у «нормы» и у прогнозов v2 — `null`).
`likely_kind` / `likely_kind_label` — самый вероятный вид и готовая строка для диспетчера («Вероятнее всего: потеря
связи (97 % вероятности отказа)»). Поля есть в `/api/predictions`, `/api/journal` и в прогнозе карточки датчика.
`GET /api/model/metrics` дополнительно отдаёт `recall_by_kind`, `by_group` (газовые / пожарные / охранные / прочие),
`comparison` (v2 и v3 на тесте на новой и старой метке) и `label_note` — почему изменилась метка.

`outcome: null` — горизонт прогноза ещё не закрылся. `decision` — последнее решение на момент `at` (`{id, decision_type, decision_label, reason, comment, user, created_at, source}`); `source: simulation` — решение смоделировано ([SIMULATED_DECISIONS.md](SIMULATED_DECISIONS.md)), в интерфейсе — бейдж «смоделировано».

### Журнал

| Метод и путь | Назначение |
|---|---|
| `GET /api/journal` | прогнозы с решениями, исходами и заявками, от новых к старым. Период `date_from`–`date_to` (по умолчанию 7 дней до последнего среза прогнозов не позже `at` — «сейчас» после конца данных не даёт пустой журнал); в строке — `work_order_id`, `work_order_number` (`ЗН-…`), `work_order_status`; `risk_level`, `decision` (`none` — без решения), `outcome` (`happened`, `not_happened`, `unknown`), `object_id`, `system_type`, `sensor_type`, `q`; `only_alerts=true` — только риск/критично и прогнозы с решением |
| `GET /api/export/journal` | те же фильтры → файл XLSX (до 50 000 строк); `format=xml` — то же в XML (см. «Обмен XML») |

| `GET /api/events` | журнал тревожных событий и смен статуса (`events_recent`): период `date_from`–`date_to` (по умолчанию сутки до последнего события не позже `at`, не длиннее 31 дня), `object_id`, `channel_id`, `system_type`, `sensor_type`, `q`, `only_alarms` (по умолчанию true), `kind` (`status` — смены статуса и служебные коды, `values`, `all`), `tag`. В строке: время, датчик, объект, пикет, значение и его вид (`status`, `number`, `service`, `date`), флаг «тревожное», `tags[{code, label, reason}]` |
| `GET /api/export/events` | те же фильтры → XLSX (до 50 000 строк) с колонками «Контекст» и «Почему»; `audit_log` — `export_events` |
| `GET /api/export/decisions` | решения с прогнозом и исходом — CSV для дообучения: `date_from`, `date_to` (до 92 дней), `source=all|user|simulation`; `audit_log` — `export_decisions` |

Контекст событий (`tags`) — прозрачные правила, не ML (`backend/app/event_context.py`): `planned_check` — «Обнаружен
газ» или газ ≥ 1 % в будни 9–14 (плановые проверки баллонами; 88 % таких событий по данным 2023–2026);
`group_off` — «Неисправен» / «Отключено устройство» / «Обесточен», и в ±12 ч так же отключились или потеряли связь
≥ 80 % и не меньше 5 однотипных датчиков подобъекта или комплекса (правило v3); `value_failure` — служебный код
(-127, -100, 255, 327,68, -3276,8…, |x| ≥ 1000), дата вместо показания или отрицательный газ.

В строке журнала — `recommendation`: `{rule_id, title, action, priority, fault_kind_label}` (коротко; полная —
`GET /api/predictions/{id}/recommendation`). В XLSX — колонка «Рекомендация» («название: действие»).

### Заявки

| Метод и путь | Назначение |
|---|---|
| `POST /api/work-orders` | черновик. Из `prediction_id` сами подставляются датчик, объект и — **по рекомендации по ТО** — приоритет, срок, исполнитель, рекомендация (`recommendation_id` = строка правила `rule:<id>`, `recommendation_text` = действие) и описание (обоснование, «чего не делать», причины прогноза). Явно переданные поля важнее. Можно по `channel_id` без прогноза (тогда рекомендация — по типу датчика). **Одна открытая заявка на датчик:** если по датчику уже есть заявка «черновик», «отправлена» или «в работе» (фактический статус, без учёта `at`) — **409** `{detail, work_order: {id, number, status, status_label}}`, новая не создаётся; после «выполнена» или «отменена» — можно. Одновременные запросы (двойной клик) выстраиваются блокировкой строки датчика — создаётся одна заявка. Чужой датчик — по-прежнему 404 без номера |
| `GET /api/work-orders` | список: `status` (несколько), `priority`, `object_id`, `channel_id`, `prediction_id`, `q` |
| `GET /api/work-orders/{id}` | заявка |
| `PATCH /api/work-orders/{id}` | правка и смена статуса: `draft → submitted → in_progress → done`, `cancelled` из любого открытого. Недопустимый переход или правка закрытой — 409 |
| `DELETE /api/work-orders/{id}` | удалить **черновик** (ошибочный или созданный при проверке) — автору или admin; не черновик — 409, чужой — 403. Пишется в `audit_log` (`work_order_delete`) |

Техник (право `work_order_status` без `work_orders`) в `PATCH` может передать только `status`, иначе 403.

### Рекомендации по ТО

Прозрачные правила, не ML (проект правил, требует согласования) — [RECOMMENDATIONS.md](RECOMMENDATIONS.md).

| Метод и путь | Назначение |
|---|---|
| `GET /api/predictions/{id}/recommendation` | действие, обоснование (факты → вывод), приоритет, срок, исполнитель, «чего не делать», предполагаемый вид отказа. Факты — на момент среза прогноза |
| `GET /api/maintenance/plan` | «Рекомендованные работы»: профилактика на ближайшие дни по правилам, без открытых заявок, по объектам (сначала срочные). `object_id`, `limit`/`offset` — по объектам. Кэшируется |
| `POST /api/maintenance/drafts` | (dispatcher, engineer, admin) `{prediction_ids: [...]}` (1–100) → черновики по рекомендациям: `{created: [WorkOrderOut], skipped: [{prediction_id, reason}]}`. Пропускаются датчики с открытой заявкой и рекомендации без заявки; для правил «на объект» — одна заявка на объект, остальные датчики — в описании |

Пример `GET /api/predictions/50401/recommendation` (демо, 01.08.2026 12:00):

```json
{
  "prediction_id": 50401, "channel_id": 334609, "at": "2026-08-01T12:00:00",
  "rule_id": "fault_diagnostics", "title": "«Неисправен» — выезд с диагностикой",
  "action": "Выезд с диагностикой: питание и шлейф датчика, адресный модуль, контакты и крепление; при повторе — замена датчика.",
  "reason": "6 сообщений «Неисправен» за сутки (обычно 0); статус менялся 40 раз за сутки (обычно 2) — дребезг → система мониторинга сообщает «Неисправен» — связь с устройством потеряна, причину выясняет выезд.",
  "facts": ["6 сообщений «Неисправен» за сутки (обычно 0)", "Статус менялся 40 раз за сутки (обычно 2) — дребезг"],
  "priority": "critical", "priority_label": "Аварийный", "due_hours": 4.0, "due_at": "2026-08-01T16:00:00",
  "assignee": "Бригада КИПиА", "avoid": [],
  "fault_kind": "fault", "fault_kind_label": "«Неисправен» (связь с устройством)",
  "fault_kind_basis": "сообщения «Неисправен» / «Отключено устройство»",
  "plan": false, "work_order_needed": true, "recommendation_id": 23,
  "source": "Проект правил, требует согласования со специалистами эксплуатации", "rules_version": "2026-09-25"
}
```

`fault_kind`: `link` — потеря связи, `fault` — «Неисправен» (по ответу заказчика — потеря связи с устройством),
`power` — питание, `drift` — недостоверные показания, `unknown`. `work_order_needed: false` — заявка не нужна
(«Наблюдение», «Плановое ТО»).

Регламентный срок (поля добавлены 28.09, старые не менялись): `due_limit_hours` — срок устранения «не более» по
регламенту эксплуатации коллекторов (РТЭКК) для правила и группы датчика, `due_basis` — основание одной фразой;
`due_hours = min(срок по приоритету или правилу, due_limit_hours)`. У правил без аналога в регламенте (наблюдение,
плановые работы, удалённая проверка) и у групп без нормы оба поля — `null`. Пример для датчика дыма с потерей связи:

```json
"due_hours": 48.0, "due_limit_hours": 48.0,
"due_basis": "по регламенту — не более 48 ч (ОПС, кат. III), РТЭКК п. 10.3.6–10.3.7, табл. 10.2; по аналогии"
```

«По аналогии» — сопоставление вида отказа с категорией регламента сделано командой и требует согласования
([RECOMMENDATIONS.md](RECOMMENDATIONS.md#сроки-по-регламенту-ртэкк)). В описании черновика заявки из рекомендации
добавляется строка «Срок: … (основание)».

### Уведомления

| Метод и путь | Назначение |
|---|---|
| `GET /api/notifications` | лента **новых переходов в «Критично»** за `hours` (по умолчанию 24) до последнего среза не позже `at`: канал критичен в срезе и не был критичным ни в одном срезе за 24 ч до него (один канал — не чаще раза в сутки). `groups` — число переходов по срезам |
| `GET /api/notifications/stream` | **SSE**. Сначала `event: snapshot` (новые переходы в «Критично» за 24 ч до `at`: по срезу до трёх отдельных уведомлений и сводка `kind: "critical_summary"` с `count` — «ещё N датчиков перешли в «Критично»»), затем `event: critical_prediction` на каждый новый переход (тот же формат, в том числе сводки), `: ping` раз в 15 с; во время симуляции — ещё служебное `event: sim_clock` (`{active, day, speed, model_time, snapshot_at}`) при смене среза, запуске и остановке — клиенты, которым оно не нужно, его просто не слушают. Доступ — одноразовый `?ticket=` (JWT в адресе не принимается) или заголовок Authorization. **Область видимости:** подписчик получает только уведомления по датчикам своей области; отдельные уведомления и сводки «ещё N» собираются для каждой области подписчиков отдельно — чужие счётчики не видны |
| `POST /api/notifications/ticket` | одноразовый тикет для SSE по обычному JWT: `{ticket, expires_in: 60}`, сгорает при подключении |
| `POST /api/notifications/test` | (право `data_import`: инженер данных, администратор; получат только подписчики, в чьей области датчик) разослать в SSE критические прогнозы среза `at` — для проверки всплывающего окна и звука |

```js
const { ticket } = await (await fetch('/api/notifications/ticket', { method: 'POST', headers: { Authorization: `Bearer ${jwt}` } })).json();
const es = new EventSource(`/api/notifications/stream?ticket=${ticket}&at=${at}`);
// тикет одноразовый: при обрыве закрыть es и подключиться заново с новым тикетом
es.addEventListener("snapshot", (e) => setCritical(JSON.parse(e.data)));
es.addEventListener("critical_prediction", (e) => notify(JSON.parse(e.data)));
```

| Метод и путь | Назначение |
|---|---|

#### Обмен XML

ТЗ, раздел 7: «Программный обмен (API): JSON, XML». Проверки и лимиты те же, что у JSON и CSV. Разбор — `defusedxml`
с запретом DTD, сущностей и внешних ссылок: XXE (`<!ENTITY x SYSTEM "file:///etc/passwd">`), «миллиард смешков»
и внешние DTD отклоняются (422) до разбора содержимого (тесты `tests/test_xml.py`). Пространства имён допускаются,
поля можно давать элементами или атрибутами.

Поток событий — `Content-Type: application/xml` (или `text/xml`):

```xml
<?xml version="1.0" encoding="UTF-8"?>
<events>
  <event>
    <event_id>3008235019</event_id>
    <channel_id>334609</channel_id>
    <ts>2026-08-01T12:00:05</ts>
    <is_alarm>false</is_alarm>
    <value>Норма</value>
  </event>
  <event channel_id="334609" ts="2026-08-01T12:00:10" is_alarm="t" value="Неисправен"/>
</events>
```

Ответ — тот же JSON `IngestResult`; ошибки проверки — 422 в том же формате, что для JSON (`loc: ["body", "events", 0, …]`).

Импорт файла `.xml` — записи в корне, имена полей те же, что заголовки CSV:

```xml
<rows>
  <row><ид_канала_данных>334609</ид_канала_данных><дата>06.08.2026</дата><время>09:00:00</время>
       <тревожное>f</тревожное><значение_датчика>Норма</значение_датчика></row>
  <row channel_id="334609" ts="2026-08-06T09:05:00" is_alarm="t" value="Неисправен"/>
</rows>
```

Выгрузка журнала — `GET /api/export/journal?format=xml&…` (те же фильтры):

```xml
<?xml version='1.0' encoding='utf-8'?>
<journal at="2026-08-03T00:00:00" rows="300">
  <prediction id="50401">
    <at>2026-08-01T12:00:00</at>
    <channel_id>334609</channel_id>
    <channel>Дым ПК 1101+2</channel>
    <prob>0.87</prob>
    <risk_level>critical</risk_level>
    <factors>6 сообщений «Неисправен» за сутки (обычно 0); …</factors>
    <outcome>happened</outcome>
    <recommendation_rule>fault_diagnostics</recommendation_rule>
    <recommendation>«Неисправен» — выезд с диагностикой: …</recommendation>
  </prediction>
</journal>
```

Поля: `at, channel_id, channel, sensor_type, system_type, object_id, object, prob, health, risk_level, factors,
factors_model, decision, decision_reason, decision_comment, decision_user, outcome, fault_at, work_order,
work_order_status, recommendation_rule, recommendation`; пустые поля не пишутся.

### Симуляция потока

Проигрывание выбранных суток по **заранее рассчитанным** прогнозам с ускорением; онлайн-пересчёта моделью нет. Устройство — [ARCHITECTURE.md](ARCHITECTURE.md#симуляция-потока-событий-вариант-б).

| Метод и путь | Назначение |
|---|---|
| `GET /api/sim/state` | (любая роль) `enabled` (`SIM_ENABLED`), `active`, `day`, `speed`, `model_time`, `snapshot_at`, кто и когда запустил, `stop_reason` (`manual`, `finished`, `restart`), счётчики `events_received`/`events_accepted`/`critical_sent`, доступные сутки `available_from`–`available_to`, `default_day`, `note` |
| `POST /api/sim/start` | (engineer, admin) `{day: "2026-06-15", speed: 60}`. Скорость 1–600; сутки без прогнозов — 422 с подсказкой диапазона; вторая симуляция — 409; `SIM_ENABLED=false` — 403. Пишется `sim_start` в `audit_log` |
| `POST /api/sim/stop` | (engineer, admin) остановить; повторный вызов безопасен. Пишется `sim_stop` |

Пока симуляция активна:
- запросы **без** `at` работают на модельное время (срезы не позже него); явный `at` работает как раньше;
- `outcome` прогнозов, чей горизонт (`at + 24 ч`) по модельному времени ещё не закрылся, — `null`; фильтр журнала `outcome=happened|not_happened` их не находит, `unknown` — находит;
- новые критические прогнозы каждого среза уходят в SSE (`critical_prediction`, формат `NotificationItem`): до 5 по отдельности, остальные — одним сводным «Ещё N новых критических прогнозов»;
- `POST /api/ingest/events` принимает события как обычно и добавляет их к счётчикам симуляции.

Скрипт `backend/scripts/simulate_stream.py` делает то же, что ТЗ называет симулятором: `POST /api/sim/start`, затем события суток порциями в `POST /api/ingest/events` в темпе модельных часов, в конце или по Ctrl+C — `POST /api/sim/stop`.

Правила чистки событий (и в импорте, и в потоке): флаг `f/t`, `false/true`; значение читается строкой и раскладывается на число и текст; значения-даты (`01.01.1970 03:00:00`) выбрасываются; дубли по связке «канал, время, значение» пропускаются; события неизвестных каналов отбрасываются.

Формат прогнозов от ML (`kind=predictions`): `channel_id, at, horizon_h, prob, health, risk_level, top_factors, model_version`; `top_factors` — JSON-список `{feature, value, norm, phrase}`. Если `health` или `risk_level` пустые, они вычисляются из `prob`. Критические прогнозы последнего загруженного момента уходят в SSE.

## Кэш тяжёлых агрегатов

«Точность за 30 дней» (`/api/dashboard/summary`), «прогноз против факта» (`/api/model/metrics`) и «Рекомендованные работы» (`/api/maintenance/plan`, ещё и по версии заявок и файла правил) считаются по миллионам
строк прогнозов и исходов (на реальных данных 2,5 и 4,8 с). Результат кэшируется в памяти процесса API (`app/cache.py`):
ключ — параметры запроса, **область видимости пользователя** и версия данных (`max(id)` прогнозов и исходов + счётчик изменений, который сбрасывают импорт
и разметка исходов, а также изменение настроек), срок жизни 15 минут. При старте API прогревает кэш для момента «Последние данные». Повторное
открытие — 0,2 с. Решения и заявки в эти агрегаты не входят и кэш не сбрасывают.
