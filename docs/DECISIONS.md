# Принятые решения

Одна строка — одно решение. Если решение неверное, поправьте его здесь и в коде.

## Общие

- Основная СУБД — PostgreSQL 16. SQLite используется только в `backend/tests` (in-memory), в основном коде нет SQLite-хаков.
- Все метки времени — московское время без часового пояса (`timestamp without time zone`), как в журналах заказчика. Если `at` приходит с поясом, он переводится в МСК.
- `at` не задан → текущее московское время. Срез прогнозов — последний `predictions.at` не позже `at` («последний расчёт на тот момент»).
- В ответе `GET /api/predictions` поле `at` — запрошенный момент (как в примере ТЗ), а не момент среза. Момент среза отдают `/api/dashboard/summary` и `/api/objects` в поле `snapshot_at`.
- Форма `GET /api/predictions` точно повторяет пример из ТЗ фронтенда (`at, total, items[]`), без лишних полей верхнего уровня. Пагинация — через `limit/offset` в запросе, `total` в ответе.
- `outcome` отдаётся всегда, когда он известен (в режиме машины времени это и есть «что случилось в следующие 24 ч»). `null` — горизонт ещё не закрылся или разметки нет.
- Решения и заявки датируются параметром `at` запроса (`created_at = max(at, prediction.at)`), чтобы в режиме машины времени созданное сразу было видно на экране этого момента. Реальное время действия пишется в `audit_log.ts`.
- Решения по прогнозу хранятся историей; актуальное — последнее по `id`, с учётом `created_at <= at`.
- «Каналы в зоне риска» — уровни `risk` и `critical`. «Прогнозы отказов на 24 ч» — `prob >= рабочий порог` (выбранная строка `model_thresholds`, иначе 0.5).
- «Точность за 30 дней» считается по парам «датчик × срез» с `at` в окне `(at − 30 д, at − 24 ч]`, то есть только по прогнозам с закрытым горизонтом.
- Журнал по умолчанию: последние 7 дней до `at`, только тревожные (`risk`, `critical`) и прогнозы с решением (`only_alerts=true`).
- Уровень риска по индексу здоровья — как в ТЗ ML: ≥80 норма, 50–79 внимание, 20–49 риск, <20 критично. `health = round(100 × (1 − prob))`.
- В `predictions` уникальный ключ `(channel_id, at, horizon_h)`, без `model_version`: в каждый момент активна одна модель, повторная загрузка перезаписывает прогноз.
- `top_factors` хранится как пришёл от ML (список `{feature, value, norm, phrase}`); в API `factors` — первые три `phrase`, полная структура — в `factors_detail` карточки прогноза.
- Статусы заявки: `draft → submitted → in_progress → done`, отмена (`cancelled`) — из любого незакрытого. Закрытую заявку менять нельзя (409). Номер — `ЗН-<год>-<id:06d>`.
- При создании заявки из прогноза приоритет берётся из риска (critical→critical, risk→high, attention→medium, normal→low), срок — из приоритета (4 ч / 24 ч / 3 дня / 7 дней).
- Роли: чтение — все роли; решения и заявки — dispatcher, engineer, admin; импорт и поток событий — engineer, admin; manager только читает и выгружает.
- Пароли — PBKDF2-SHA256 из стандартной библиотеки (без passlib/bcrypt). JWT — HS256, `JWT_SECRET` из `.env`.
- Swagger: кнопка Authorize работает через `POST /api/auth/token` (форма OAuth2); фронтенду — `POST /api/auth/login` (JSON). Ответ одинаковый.
- SSE: EventSource не умеет заголовки, поэтому браузер берёт одноразовый тикет (`POST /api/notifications/ticket`) и подключается с `?ticket=`. Ранний вариант с `?token=<JWT>` убран при аудите безопасности ([SECURITY_AUDIT.md](SECURITY_AUDIT.md)).
- SSE-брокер живёт в памяти одного процесса (uvicorn без `--workers`). Для нескольких воркеров — LISTEN/NOTIFY, см. `app/notifications.py`.
- Пока нет ML и симулятора, новые критические прогнозы в SSE появляются при `POST /api/import` с `kind=predictions` и при `POST /api/notifications/test`.
- `POST /api/ingest/events` сохраняет события в `events_recent`, онлайн-пересчёта прогнозов нет: прогнозы рассчитываются пакетно в `ml/` ([ARCHITECTURE.md](ARCHITECTURE.md)).
- Ручной импорт ограничен 50 МБ; гигабайтные журналы — через ETL (`app/etl`, `ml/`). Правила чистки из ТЗ реализованы в `app/importer.py` и будут переиспользованы в ETL.
- Тег `847-1.1.131.2.` раскладывается на уровни `847 / 1 / 1 / 131 / 2` (часть до дефиса — отдельный уровень), хранится до 5 уровней.
- Сообщения об ошибках — на русском; ответы 422 от Pydantic переводятся в `app/errors.py` с сохранением структуры FastAPI.
- Списки заявок и счётчик открытых заявок учитывают только заявки с `created_at <= at`; закрытая позже `at` считается открытой на тот момент.
- Отказы для графика карточки датчика — таблица `channel_faults` (миграция `0002`): разметка ML всех трёх видов, включая «Пропадание связи», которого нет в событиях (это отсутствие событий). Грузится `ml/db/load_postgres.py` (`--only faults` — только она). `history` объединяет её со статусами-отказами из `events_recent`, поэтому демо-сид и входящий поток отмечаются без изменений; совпадения (время, вид) схлопываются.
- Удалять можно только черновики заявок (`DELETE /api/work-orders/{id}`) — автору или admin, с записью в аудит. Отправленные заявки только отменяются: у них уже есть история. Так проверки (`npm run check:real`) убирают за собой тестовые заявки, не трогая настоящие.
- `docker-compose.yml` работает и без `.env` (значения по умолчанию), поэтому `docker compose up` не требует ручных шагов.

## Демо-сид

- Сид детерминированный (`random.Random(20260922)`) и идемпотентный: если пользователи уже есть, он ничего не делает; `--force` пересоздаёт данные.
- Период демо — 01.07.2026–31.08.2026 (ТЗ: «1–2 месяца событий»), срезы прогнозов каждые 6 ч. Масштаб `small` (60 датчиков, 27.07–04.08) — для тестов.
- Пример из ТЗ фронтенда воспроизводится буквально: датчик 334609 «Дым ПК 1101+2», объект 20 «объект Фита» (Район → объект Бета → объект Фита), `at=2026-08-01T12:00`, prob 0.87, отказ в 18:42:10. `prediction_id` при этом не 90211, а тот, что выдаёт генерация.
- Прогнозы, исходы, события и метрики выводятся из одного процесса отказов. Метрики и таблица порогов считаются по сгенерированным прогнозам так же, как в ТЗ ML: срезы «датчик × сутки» в 00:00, без срезов с отказом за последние 72 ч, рабочий порог — максимальный Recall при Precision ≥ 0.72.
- Precision@K на демо-наборе низкий (P@20 ≈ 0.14): в нём 400 датчиков и около 4 отказов в сутки. Это честное значение для малого набора; реальное придёт от ML.
- `events_recent` в сиде прореженный: числовые датчики — раз в 2 часа, статусные — 2 «Норма» в сутки плюс события вокруг отказов. Поэтому `events_count` в `channel_daily` меньше реального потока (~140 в сутки у газовых).
- Датчики привязаны только к подобъектам (уровень 3). Версия модели — `lgbm-2026.09-demo`.

## Места, зависящие от диалекта БД (проверить на PostgreSQL)

Все такие места помечены в коде комментарием `# DIALECT:` (`grep -rn DIALECT backend/app`).

**Проверка 24.09.2026** на локальном PostgreSQL 16.10 (портативная сборка EDB под Windows, не в Docker): `alembic upgrade head` и `alembic check` без расхождений, демо-сид (≈24 с), все 43 теста с `TEST_DATABASE_URL`, ручные запросы к живому uvicorn, `EXPLAIN ANALYZE` основных запросов.

| Где | Что | Как ведёт себя в PostgreSQL | Проверка на PG 16 |
|---|---|---|---|
| `app/models.py` — `JSONType` | `JSON().with_variant(JSONB(), "postgresql")` для `predictions.top_factors`, `audit_log.details` | колонка `JSONB`; миграция `0001` создаёт именно JSONB, `alembic check` расхождений не видит | ✅ |
| `app/dbcompat.py` — `upsert()` | `INSERT … ON CONFLICT DO NOTHING / DO UPDATE` через `dialects.postgresql.insert` | нативный ON CONFLICT по уникальным ключам | ✅ |
| `app/dbcompat.py` — `upsert()`, подсчёт строк | число вставленных строк | **`rowcount` через psycopg приходит как −1** — на SQLite тесты этого не видели. Исправлено: счёт через `RETURNING` | ✅ исправлено |
| `app/dbcompat.py` — `day_of()` | `date(at)` для группировки по дням в `/api/model/metrics` | возвращает `date`; в SQLite — строку, приводится `as_date()` | ✅ |
| `app/dbcompat.py` — `reset_sequences()` | `setval(pg_get_serial_sequence(…))` после вставки с явными id в сиде | сдвигает последовательности; новые решения и заявки после сида создаются без конфликтов id | ✅ |
| `app/services.py`, `app/api/work_orders.py` — поиск `q` | `ilike` | `ILIKE`, seq scan по каналам — приемлемо для 11 тыс. строк; при нужде pg_trgm | ✅ |
| `app/api/channels.py` — сортировка | `prob DESC NULLS LAST` | нативно | ✅ |
| `app/api/work_orders.py` — рекомендация по умолчанию | `ORDER BY sensor_type IS NULL` (boolean) | false < true, как и нужно | ✅ |
| Индексы `predictions` | срез `max(at) ≤ :at` и `at = :snap ORDER BY prob DESC` | `Index Scan Backward` по `ix_predictions_at_prob`, < 1 мс на 99 тыс. строк | ✅ |
| `alembic/versions/0001_initial_schema.py` | миграции только под PostgreSQL (`BIGSERIAL`, `JSONB`) | применяется на чистой базе | ✅ |
| `tests/conftest.py` | BIGINT → INTEGER для SQLite (автоинкремент), `PRAGMA foreign_keys` | только тесты, в основной код не попадает | — |
