# Рекомендации по техническому обслуживанию

> **Проект правил — требует согласования со специалистами эксплуатации.** Правила составлены по данным журналов
> заказчика, ответам заказчика в чате хакатона и здравому смыслу обслуживания. **Сроки ограничены сверху
> регламентом эксплуатации коллекторов** — «Регламент выполнения работ по технической эксплуатации городских и
> внутриквартальных коммуникационных коллекторов в городе Москве» (РТЭКК): числа и пункты взяты из его текста,
> а сопоставление наших видов отказа с категориями регламента — интерпретация команды, помечена «по аналогии»
> и требует согласования ([Сроки по регламенту](#сроки-по-регламенту-ртэкк)).

Общий ТЗ требует «формирования рекомендаций по техническому обслуживанию на основе данных о состоянии оборудования»
(разделы 4 и 6), а финальная экспертиза сравнивает «сгенерированные сервисом рекомендации с реальными при текущих
вводных». Поэтому рекомендация строится не по типу датчика, а по тому, **что с ним происходит**: вид отказа, история,
соседи по объекту, питание, заявки. Это прозрачные правила, а не ML — каждое решение можно проверить глазами.

## Где видно

- **Карточка датчика** — блок «Рекомендация по обслуживанию» сразу под прогнозом: что сделать, почему (факты →
  вывод), приоритет, срок, кому, чего не делать; вид отказа — метка с подсказкой, на чём он основан. Кнопка
  «Заявка по рекомендации» открывает форму, уже заполненную из рекомендации (действие, срок, приоритет,
  исполнитель, описание с обоснованием и причинами прогноза); диспетчер может изменить любое поле. Кнопка
  «Создать заявку» в блоке прогноза заполняет форму так же.
- **Журнал прогнозов** — колонка «Рекомендация» (на широких экранах; полный текст — в подсказке), в XLSX —
  колонка «Рекомендация», в XML — `recommendation_rule` и `recommendation`.
- **Заявки → «Рекомендованные работы»** — профилактика на ближайшие дни (ТЗ, раздел 3: «поддержка планирования
  профилактических работ»): датчики с повторными отказами, повтором после ремонта, недостоверными показаниями,
  проблемами агрегатов, питания или связи объекта — и без открытой заявки. Сгруппированы по объектам, сначала самые
  срочные. Выбранным — «Создать черновики заявок»; для правил «на объект» (массовая потеря связи, питание) создаётся
  одна заявка на объект, остальные датчики перечисляются в её описании.
- **API:** `GET /api/predictions/{id}/recommendation`, `GET /api/maintenance/plan`, `POST /api/maintenance/drafts`
  ([API.md](API.md)). `POST /api/work-orders` с `prediction_id` подставляет поля из рекомендации.

## Как устроено

Код — `backend/app/recommendations/engine.py`, правила — `backend/app/recommendations/rules.yaml`.

1. **Факты на момент прогноза** (всё строго не позже `p.at` — «машина времени» и симуляция не видят будущего;
   запросов — константа на пачку прогнозов, а не на прогноз):
   - причины прогноза (`top_factors`: коды признаков и значения);
   - отказы канала за 30 и 90 дней по видам — из разметки ML `channel_faults` (в демо её нет — там дни с
     сообщениями о неисправности из `channel_daily`);
   - свои сообщения «Неисправен» / «Отключено устройство» / «Обесточен» за сутки (`events_recent`);
   - **соседи по объекту**: сколько других датчиков того же объекта сейчас молчат (прогноз «Риск» и выше из-за
     тишины в том же срезе или потеря связи по разметке за сутки) и сколько датчиков объекта всего;
   - **питание объекта**: у скольких датчиков фаз объекта за сутки появилось «Обесточен», которого неделю до этого
     не было;
   - заявки по датчику: открытая, выполненная за последние 14 дней и отказы после неё;
   - точность модели (Precision) по типу датчика из `model_metrics`.
2. **Вид отказа** — одна функция `infer_fault_kind`: потеря связи, «Неисправен», питание, недостоверные показания,
   не ясен. Сейчас он выводится из причин и фактов (тишина → потеря связи; «Неисправен»/«Отключено устройство» за
   сутки или дребезг → «Неисправен»; новое «Обесточен» у своей фазы или у фаз объекта при тишине → питание;
   «застывшие» или расходящиеся с соседями показания → недостоверные показания; иначе — самый частый вид за 90 дней).
   **Это единственная точка**: когда модель v3 начнёт отдавать вероятности по видам отказа, они придут в
   `Context.kind_probs` и будут взяты первыми (тест `test_fault_kind_from_model_probabilities_first`).
3. **Правила** проверяются сверху вниз, срабатывает первое, у которого выполнены все условия. Последнее правило —
   без условий, поэтому рекомендация есть всегда.
4. **Обоснование** собирается из фактов, которые указаны у правила, и вывода: «Датчик молчит 5 сут 10 ч — обычно
   выходит на связь хотя бы раз в 5 сут 16 ч…; у 22 соседних датчиков объекта (из 200) тоже пропадает связь →
   вероятна проблема линии связи или шкафа объекта, а не датчика».
5. **Приоритет** — по уровню риска (или на ступень выше, или фиксированный), не ниже `priority_min` правила и не ниже
   порога группы датчика (`min_priority_by_group`: газовые — не ниже «высокого», дым и пожарные — не ниже
   «среднего»; заказчик: приоритет типов — газовые, пожарные, охранные). **Срок** — у правила или по приоритету
   (аварийный 4 ч, высокий 24 ч, средний 3 сут, низкий 7 сут), но **не больше регламентного** (РТЭКК, см. ниже):
   срок = min(срок по приоритету, срок по регламенту). Основание срока показывается рядом одной фразой.
6. **Чего не делать** — у правила и общие оговорки: по датчику уже открыта заявка → не создавать повторную; заявка
   выполнена меньше суток назад и отказов после неё не было → не выезжать повторно; массовая тишина газовых
   датчиков → сначала сверить с графиком ППР АКМ (по графику заказчика датчики метана демонтируются на ≈ 10–15 дней,
   в данных это выглядит как групповая потеря связи).

Одинаковые входы дают одинаковый выход (в движке нет случайности и текущего времени) — тест
`test_same_input_same_output`; ответ API стабилен между запросами — `test_recommendation_endpoint`.

### Почему пороги такие (по данным)

- **Массовая потеря связи** — не меньше 3 соседей **и** не меньше 8 % объекта. Реальные «объекты» содержат по
  100–700 датчиков, и в любой срез 3–5 % из них молчат: 29.06.2026 23:00 молчали 250 из 7 654 каналов, медиана по
  объектам ≈ 5 %. «3 из 243» — это фон, а «22 из 200» — уже проблема линии или шкафа объекта.
- **«Обесточен» у фаз** — считается только новое: у части фаз оно приходит ежедневно (за сутки до 29.06 23:00 — у 37
  из 54 фаз одного объекта; похоже на штатное состояние резервных фаз). Новых за сутки — у 0–5 фаз на объект.
- **Удалённая проверка сначала** — если Precision модели по типу датчика ниже 0,5: на тесте 2026 года у датчиков
  дыма 0,258 ([ML_REPORT.md](ML_REPORT.md)), то есть примерно три тревоги из четырёх — ложные.
- **«Неисправен» — это потеря связи с устройством** (ответ заказчика 23.09): причину выясняет выезд, поэтому
  рекомендация — выезд с диагностикой связи и датчика, а не «датчик сам сообщил о поломке».

### Вид отказа в модели v3

С модели `lgbm-2026.09-v3` вид отказа приходит из `kind_probs` прогноза: вероятности «потеря связи» (`link`),
«Неисправен» (`fault`), «Отключено устройство» (`disconnected`) и «Сбой значения» (`value`) — это единственная точка
`infer_fault_kind` в `engine.py`. Раньше проверяется групповое отключение: молчит ≥ `group_silence_share` (0,5)
однотипных датчиков объекта — по признаку `nb_silent_share` среди причин или по данным на момент прогноза
(`same_type_silent` / `same_type_channels`). Это то же понятие, что и в разметке v3 (`docs/ML_V3_PLAN.md`, раздел 2):
плановые работы или отключение объекта — не отказ отдельного датчика. Без `kind_probs` (прогнозы v2 и уровня «норма»)
вид выводится из причин, как раньше. На реальных данных после загрузки v3 (срезы 16.02, 27.04 и 15.06.2026, по 500
прогнозов журнала): «Групповое отключение» — 63 / 87 / 76, «Сбой значения — проверка передачи» — 7 / 5 / 2, «Массовая потеря связи в объекте» — 157 / 237 / 252 (см. раздел
проверки ниже).

## Сроки по регламенту (РТЭКК)

Регламент задаёт **максимальные** сроки устранения неисправностей («не более», отсчёт — с момента обнаружения
или поступления сообщения). Срок в рекомендации = min(срок по приоритету или правилу, регламентный): регламент
ограничивает сверху, срочные случаи (аварийный — 4 ч) не удлиняются. Карточка датчика, «Рекомендованные работы»
(подсказка к сроку) и описание черновика заявки показывают основание, например: «Срок: 48 ч (по регламенту —
не более 48 ч (ОПС, кат. III), РТЭКК п. 10.3.6–10.3.7, табл. 10.2; по аналогии)».

«Прямая норма» — пункт регламента прямо про этот случай; «по аналогии» — наш вид отказа (он виден по данным
мониторинга) сопоставлен с категорией регламента командой. Это сопоставление нужно согласовать со специалистами
эксплуатации.

|---|---|---|---|---|---|

III — периодические отказы извещателей с самовосстановлением) | 10.3.6–10.3.7, табл. 10.2 | по аналогии |

## Как настраивать

Всё — в `backend/app/recommendations/rules.yaml`, код менять не нужно:

- `params` — пороги: `mass_link_neighbors` и `mass_link_share` (массовая потеря связи), `power_quiet_days`,
  `low_precision`, `flap_changes` (дребезг), `repair_days`, `due_hours` (сроки по приоритету),
  `min_priority_by_group`;
- `rules` — порядок, условия, действие, факты обоснования, вывод, приоритет, срок, исполнитель, «чего не делать»,
  попадание в «Рекомендованные работы» (`plan`), одна заявка на объект (`per_object`), нужна ли заявка
  (`work_order`);
- `sensor_groups` — какие типы датчиков к какой группе относятся;
- `regulation` — нормы регламента: срок «не более» в часах, подпись, пункт, категория, примечание;
- `due_limits` — наборы регламентных сроков: случаи с теми же условиями, что `when` (группа датчика, массовость
  и т. д.), первый подошедший задаёт норму; `direct: true` — прямая норма, иначе «по аналогии». Правило ссылается
  на набор полем `due_limit`; правило без него получает срок как раньше. Неизвестная норма, набор или условие —
  ошибка при загрузке (`test_regulation_errors_are_loud`).

API перечитывает файл при изменении (по времени изменения файла), перезапуск не нужен; файл с ошибкой (неизвестное
условие, факт, группа или приоритет, нет последнего правила без условий) не принимается — тесты
`test_rules_file_errors_are_loud`. При старте API справочник `recommendations` дополняется строками правил
(`code = rule:<id>`, текст = действие): так рекомендация правила выбирается в форме заявки из того же справочника,
что и прежние рекомендации по типам датчиков. Прежние строки не меняются; правило, удалённое из файла, становится
неактивным (на него могут ссылаться заявки).

Уровни риска, от которых зависят правила, администратор меняет в «Настройках» ([API.md](API.md), «Настройки»).

## Ограничения

- **Проект правил.** Нужна сверка со специалистами эксплуатации: формулировки работ, исполнители, пороги.
  Регламентные сроки устранения по РТЭКК заложены, но сопоставление видов отказа с категориями регламента
  («по аналогии») — интерпретация команды; признаки подтопления, внешних причин и срабатывания газа правилами
  не учитываются (см. [Сроки по регламенту](#сроки-по-регламенту-ртэкк)).
- **Нет реестра оборудования и истории ремонтов** (заказчик не предоставит): «повтор после ремонта» опирается
  только на заявки, созданные в сервисе; линия связи и щит определяются по объекту, а не по реальной схеме подключения.
- **Вид отказа выводится из причин прогноза**, пока модель не отдаёт вероятности по видам (модель v3).
- «Соседи» — датчики того же объекта справочника; в больших объектах (сотни датчиков) это грубое приближение
  к «одному шкафу».
- Рекомендация помогает диспетчеру и не заменяет его решение (ТЗ, раздел 5: сервис не принимает окончательных решений).
