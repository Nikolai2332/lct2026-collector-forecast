# Прогноз отказов оборудования коллекторов (ЛЦТ-2026)

Сервис за 24 часа предсказывает отказы датчиков и агрегатов в подземных коллекторах Москвы (заказчик — АО «Москоллектор») и помогает диспетчеру принять решение: риск, причины, рекомендация по обслуживанию и черновик заявки на одной карточке.

Монорепозиторий:

```
backend/    FastAPI + PostgreSQL: код, миграции Alembic, демо-сид, тесты, Dockerfile, openapi.json
frontend/   интерфейс диспетчера: React + TypeScript + Ant Design, моки MSW, Dockerfile (Nginx)
ml/         ETL журналов (DuckDB → Parquet), признаки, LightGBM, прогнозы, загрузка в PostgreSQL
docs/       ТЗ, архитектура, API, решения, развёртывание
```

## Запуск одной командой

Нужны Docker с Compose 2.24 или новее (`docker compose version`), около 3 ГБ свободного места под образы и интернет для первой сборки. Порты на этой машине: 8080 (интерфейс), 8000 и 5432 (только 127.0.0.1).

```bash
docker compose up --build
```

Первая сборка — 1–3 минуты (проверено с нуля из `git archive`: сборка 36 с, до `healthy` ещё 67 с, при уже скачанных базовых образах). При первом старте API само применит миграции и засеет демо-данные (около 30 секунд). Дальше:

- интерфейс диспетчера: <http://localhost:8080> (Nginx проксирует `/api` на бэкенд)
- Swagger: <http://localhost:8000/docs>
- проверка: <http://localhost:8000/api/health>

Демо-данные — за 01.07–31.08.2026: в интерфейсе выберите момент в «машине времени» в шапке, например 01.08.2026 12:00.

Файл `.env` не обязателен: без него используются значения по умолчанию демо-режима. Swagger и порт БД доступны только с этой машины (127.0.0.1).

Если порты заняты, задайте другие через переменные окружения (или в `.env`), например в PowerShell:

```powershell
$env:FRONTEND_PORT=18080; $env:API_PORT=18000; $env:POSTGRES_PORT=15432; docker compose up --build
```

Остановить: `docker compose down` (данные в томе `pgdata` сохраняются). Повторный запуск не пересоздаёт демо-данные.

**На сервер — только production-режим:** `docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build` с `.env`, где заданы домен и свои секреты. Там TLS через Caddy, наружу только 80/443, демо-пользователи заблокированы, со слабыми секретами API не стартует. Пошагово — [docs/DEPLOY_VPS.md](docs/DEPLOY_VPS.md), модель безопасности — [docs/SECURITY.md](docs/SECURITY.md).

## Роли и демо-пользователи (только demo-режим)

Ролевая модель заказчика: **роли складываются**, область видимости — узлы дерева объектов (район или
объект-комплекс со всем поддеревом). Сервер отдаёт только данные своей области: дашборд, схема, журналы,
карточки, заявки, уведомления, выгрузки; чужой объект по прямой ссылке — «не найден». Таблица прав и LDAP —
[docs/SECURITY.md](docs/SECURITY.md#роли-и-области-видимости). На экране входа — быстрый выбор роли.

| Роль | Логин | Пароль | Область | Что может |
|---|---|---|---|---|
| Диспетчер ОДС | `ods` | `ods123` | все объекты | решения по прогнозам, заявки, симуляция |
| Диспетчер района | `dispatcher` | `dispatcher123` | дерево своего района | решения по прогнозам, заявки |
| Техник | `technician` | `technician123` | один комплекс («объект Альфа») | чтение, выгрузка, смена статуса заявок |
| Руководитель | `manager` | `manager123` | район | только чтение и выгрузки |
| Инженер данных | `engineer` | `engineer123` | все объекты | решения, заявки, импорт данных и поток событий, симуляция |
| Администратор | `admin` | `admin123` | все объекты | всё + настройки и «Пользователи и роли» |

В шапке рядом с именем — роли и область («Техник · объект Альфа»). Администратор меняет роли и области локальных
учёток в меню пользователя → «Пользователи и роли» (изменения — в журнале действий); учётки из AD получают роли и
области из групп каталога. В production демо-учётки заблокированы, а первый администратор задаётся в `.env`
(`ADMIN_USERNAME`, `ADMIN_PASSWORD`).

В Swagger нажмите **Authorize**, введите логин и пароль (client_id и secret оставьте пустыми). Фронтенд входит через `POST /api/auth/login` с JSON.

- **Воспроизвести ML с нуля** на исходных CSV — [ml/README.md](ml/README.md): 10 шагов, около 4–5 часов на мощной машине.
- **Срез реальных данных для экспертов** — архив `expert_slice_20260601_20260630.zip` (≈ 137 МБ, июнь 2026:
  прогнозы модели v3 с исходами, события, отказы, метрики; ссылку на архив даёт команда, в репозитории его нет).
  Загрузка — одна команда после `docker compose up`:

  ```bash
  docker compose cp expert_slice_20260601_20260630.zip api:/tmp/slice.zip
  docker compose exec api python -m scripts.load_expert_slice /tmp/slice.zip   # ≈ 14 минут
  docker compose restart api
  ```

  Затем войти «Диспетчером ОДС», «машина времени» — 29.06.2026 23:00: «Качество модели» — `lgbm-2026.09-v3`
  (Precision 0,696, Recall 0,571 на тесте 2026), в журнале — реальные исходы прогнозов. Что в срезе, как проверить
  и как вернуть демо — [docs/EXPERT_SLICE.md](docs/EXPERT_SLICE.md). Без среза работает синтетическое демо.
- **Перенести готовую базу с реальными прогнозами** (копия `pg_dump` ≈ 200 МБ, передаётся отдельно от кода) — [docs/DEPLOY_VPS.md](docs/DEPLOY_VPS.md), шаг 7A. На реальных данных «машина времени» работает в пределах 01.01–30.06.2026.

## Что в демо-данных

Обезличенные данные по образцу заказчика, генерируются детерминированно (`backend/app/seed.py`, фиксированный seed):

- дерево объектов: район → 16 объектов → 78 подобъектов (95 записей, как в справочнике заказчика);
- 400 датчиков 19 типов в 6 системах, названия вида «Дым ПК 1101+2», теги вида `847-1.1.131.2`;
- события и суточные агрегаты за **01.07.2026–31.08.2026**;
- прогнозы каждые 6 часов с исходами (сбылся ли отказ), все четыре уровня риска;
- решения диспетчеров, заявки в разных статусах;
- метрики модели и таблица «порог → Precision / Recall / тревог в сутки», посчитанные по этим же прогнозам.

**Машина времени:** все запросы на чтение принимают `at`. Пример из ТЗ воспроизводится буквально:

```
GET /api/predictions?at=2026-08-01T12:00:00
→ первый элемент: «Дым ПК 1101+2», вероятность 0.87, критично, отказ случился в 18:42:10
```

Пересоздать демо-данные: `docker compose exec api python -m app.seed --force`.

## Симуляция потока событий

**Что это — честно:** воспроизведение выбранных суток по **заранее рассчитанным** прогнозам. Модель во время симуляции не запускается, онлайн-пересчёта нет (признакам нужна история за 30 дней из архива журналов, которого у жюри нет, см. [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md)). Интерфейс и документация говорят об этом прямо.

**Что происходит.** На сервере идут «модельные часы» с ускорением (×60 — сутки за 24 минуты, ×600 — за 2,4 минуты). Режим «Сейчас» во всех экранах показывает модельный момент: по мере хода часов появляются прогнозы очередного среза, обновляются дашборд, схема объектов, журнал и счётчики. Новые критические прогнозы (датчик не был критичным сутки до этого среза — та же логика, что у колокольчика и ленты) приходят всплывающими уведомлениями со звуком: до 5 по отдельности, остальные — одним сводным «ещё N». Исходы, которые по модельному времени ещё не наступили, скрыты. В шапке у всех — метка «Симуляция ×60 · 01.08.2026 14:32». Выбранная вручную «машина времени» важнее симуляции; кнопка «Сейчас» возвращает к модельному времени. В конце суток симуляция останавливается сама. Данные в базе симуляция не меняет.

**Кнопкой** (роли «Диспетчер ОДС», «Инженер данных» и «Администратор»): в шапке **Симуляция** → сутки и скорость → **Запустить**. Остановить — кнопка ⏸ рядом с меткой.

**Из командной строки** — скрипт сам запускает симуляцию и проигрывает события суток в `POST /api/ingest/events` в темпе модельных часов (как в ТЗ):

```bash
docker compose exec api python -m scripts.simulate_stream --day 2026-08-01 --speed 60
```

Ctrl+C аккуратно останавливает симуляцию. События берутся из таблицы `events_recent` (или `--file журнал.csv`); уже загруженные сервер пропускает как дубли, скрипт так и пишет: «новых 0, дублей N». `--purge-day --yes` удаляет события только этих суток перед проигрышем (копия сохраняется в `sim_backup_events_<дата>.csv`, восстановление — `--file` с этим файлом). Логин по умолчанию — демо-инженер; другой: `--user/--password` или `SIM_USERNAME/SIM_PASSWORD`.

| Данные | Доступные сутки | Рекомендуем для показа |
|---|---|---|
| Демо (`docker compose up`) | 01.07–31.08.2026, срезы раз в 6 ч | **01.08.2026, ×600**: пример из ТЗ, срез 12:00 с «Дым ПК 1101+2» |
| Реальные прогнозы (копия БД) | 01.01–30.06.2026, почасовые срезы с 01.06 | **15.06.2026, ×60** (или ×600 для быстрого показа) |

Включение: `SIM_ENABLED` — в demo включено, в production выключено (для показа на сервере — `SIM_ENABLED=true` в `.env`, [docs/DEPLOY_VPS.md](docs/DEPLOY_VPS.md)). Проверка в браузере: `cd frontend && node scripts/sim-check.mjs http://localhost:8080 2026-08-01 600`.

## Схема коллектора, журнал событий, тёмная тема

- **Схема коллектора** («Схема объектов» → «Схема коллектора»): линейная схема по пикетам из названий датчиков
  (1 ПК = 10 м) — основное тело и боковые галереи каждого комплекса, датчики цветом **и формой** по риску,
  проблемные участки (скопления тревожных датчиков на оси), масштаб колесом, сдвиг, фильтры по риску, системе, типу,
  району и объекту, клик — карточка датчика. **Геометрия синтетическая** (координат у заказчика нет) — так и подписано
  в интерфейсе и API. GeoJSON и WKT — `GET /api/geo/collectors`, `GET /api/geo/channels`; разбор пикетов, допущения
  и покрытие — [docs/GEO_SCHEME.md](docs/GEO_SCHEME.md).
- **Журнал событий** («Журнал» → «События»): тревожные события и смены статуса с фильтрами и выгрузкой XLSX;
  контекст по прозрачным правилам (не ML) — «вероятная плановая проверка» (газ в будни 9–14), «групповое
  отключение — вероятно, плановые работы», «сбой значения». Те же метки — в блоке «События за 7 дней» на карточке.
- **Тёмная тема** — переключатель ☾ в шапке, выбор запоминается; графики и схема читаемы в обеих темах.
- **Смоделированные решения диспетчера** (журнала ОДС у заказчика нет): `docker compose exec api python -m
  scripts.simulate_decisions --from 2026-07-01 --to 2026-08-31` — правдоподобная история решений с бейджем
  «смоделировано»; выгрузка решений с исходами для дообучения — `GET /api/export/decisions`
  ([docs/SIMULATED_DECISIONS.md](docs/SIMULATED_DECISIONS.md)).

## Рекомендации по ТО, настройки, интеграции

- **Рекомендации по техническому обслуживанию** — по состоянию оборудования, а не по типу датчика: вид отказа, история
  отказов, соседи по объекту, питание, заявки → что сделать, почему, приоритет, срок, кому, чего не делать. Блок
  «Рекомендация» — на карточке датчика под прогнозом, заявка заполняется из рекомендации; на экране «Заявки» —
  вкладка «Рекомендованные работы» с черновиками выбранным. Прозрачные правила в
  `backend/app/recommendations/rules.yaml` — **проект правил, требует согласования со специалистами эксплуатации**.
  Подробно, таблица правил и проверка на реальных данных — [docs/RECOMMENDATIONS.md](docs/RECOMMENDATIONS.md).
- **Настройки** (администратор, меню пользователя): границы уровней риска и лимиты уведомлений — действуют сразу,
  без перезапуска, изменения — в журнале аудита.
- **Обмен XML** наравне с JSON: приём потока событий, импорт, выгрузка журнала (`format=xml`); разбор защищён от XXE
  ([docs/API.md](docs/API.md#обмен-xml)).
- **Вход через LDAP/AD** (`LDAP_ENABLED=true`): роли и область видимости по группам каталога (`LDAP_ROLE_GROUPS`,
  `LDAP_SCOPE_GROUPS`); проверено на OpenLDAP —
  `deploy/ldap-test/` ([docs/SECURITY.md](docs/SECURITY.md#ldap--active-directory)).
- **Нагрузка:** 20 пользователей — без деградации, 40 — без ошибок ([docs/LOADTEST.md](docs/LOADTEST.md));
  задержка потока: событие в карточке — 45 мс, уведомление — ≈ 1 с ([docs/ARCHITECTURE.md](docs/ARCHITECTURE.md#задержка-потоковых-данных)).
- Сверка с общим ТЗ по разделам 4–13 — [docs/TZ_COVERAGE.md](docs/TZ_COVERAGE.md).

## Разработка без Docker

Нужны Python 3.12+ и PostgreSQL 16.

```bash
cd backend
python -m venv .venv && . .venv/bin/activate      # Windows: .venv\Scripts\activate
pip install -r requirements-dev.txt
export DATABASE_URL=postgresql+psycopg://collector:change-me@localhost:5432/collector
alembic upgrade head
python -m app.seed                   # --scale small — маленький набор для быстрых проверок
uvicorn app.main:app --reload
```

Тесты (в том же venv; PostgreSQL для основного прогона не нужен):

```bash
cd backend
pytest                                # SQLite в памяти, ~50 секунд (461 тест)

# на PostgreSQL из docker compose (отдельная база, очищается тестами), ~3 минуты
docker compose exec db createdb -U collector collector_test
TEST_DATABASE_URL=postgresql+psycopg://collector:change-me@localhost:5432/collector_test pytest
# Windows PowerShell: $env:TEST_DATABASE_URL="postgresql+psycopg://..."; pytest
```

Обновить контракт после изменения API: `python scripts/export_openapi.py` (проверка актуальности — `--check`).
